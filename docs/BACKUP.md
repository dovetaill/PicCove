# 本地存储的备份与恢复

数据库保存归属、配额、相册和外链 ID，上传目录保存原图；两者必须作为同一个时间点的备份。只复制其中一个不能恢复系统。以下为操作说明，不会自动连接或修改任何生产服务。

## 备份

1. 确认实际服务的 UID/GID、数据库连接和 `UPLOAD_DIR` 真实路径，记录目录及文件的数值 UID/GID、权限、符号链接、ACL／扩展属性（如存在）。备份凭据通过受保护的配置提供，不放入命令历史或仓库。
2. 进入维护窗口，使用部署系统正常停止 PicCove API，并确认进程退出。不得按进程名称批量停止其他服务。数据库可以继续运行，但不允许其他应用写 PicCove 的表或图片目录。
3. 以有权限的非特权身份执行 `pg_dump --format=custom --file=<本次备份目录>/database.dump <目标数据库>`。归档整个实际上传目录，保留文件名和存储键，同时记录文件大小和 SHA-256 清单。`.piccove.lock` 不含业务数据，恢复副本中可省略。
4. 记录应用版本、配置中非密钥部分、数据库版本、备份时间及数据库／文件校验值。密钥需单独保护。检查命令退出状态和产物可读性，再恢复 API 服务。
5. 将这一组备份加密保存到独立于原服务器的位置。备份位置、访问身份和保留周期须在实际部署时确定；没有异机副本前不能声称已具备灾难恢复保障。

禁止为了让备份通过而递归更改既有目录权限。若服务身份无法读取文件，先核对归属与实际原因。

## 隔离恢复

1. 创建全新的数据库和任务独占图片目录。禁止覆盖生产数据库、已有图片目录或修改其权限。
2. 使用 `pg_restore --exit-on-error --dbname=<新数据库> <备份目录>/database.dump` 恢复数据库，把对应图片副本恢复到新目录。检查校验清单、文件数量与大小，按事先记录的身份及运行方案核对访问权限；不要猜测生产文件属主。
3. 给单独 API 实例指定恢复数据库、恢复目录、独立端口和测试前台 Origin。仅修改恢复实例的 `PUBLIC_BASE_URL`。首次管理员配置不会覆盖备份中的已有账号。
4. 验证用户／相册／配额数据存在、登录可用、原图片 ID 路径可访问。必须下载完整文件并比对 SHA-256，包含较大图片；响应头 200 不足以证明恢复成功。使用已有账号登录还要考虑备份中未过期的限流窗口。
5. 停止这次恢复实例及子进程，删除测试数据库、恢复目录、临时日志和产物；核对测试端口已释放及原生产路径元数据未被更改。保留正式备份，不要误删备份源。

本次开发验证在 PostgreSQL 16 临时容器中完成数据库备份／恢复，使用独立非特权 API 实例核对恢复后的 4 个账号及图片完整内容。此结果不代表实际生产备份位置、调度和保留周期已经配置。
