本文档完整呈现 **Antigravity (AGY)** 与 **Codex (`gpt-6.2-astra`)** 对 `/home/wwwroot/piccove` 全栈源码的只读审计证据链，重点回答：**问题出在哪里、为什么会产生、实际危害有多大**。

## 一、潜在漏洞与高危缺陷根因分析

### 1. 【P0 可用性/DoS 漏洞】`state.uploads` 全局互斥锁覆盖网络读取与图片访问，单连接可卡死全站
- **精确位置**：
  - 上传入口拿锁：`apps/api/src/main.rs:659` (`let _guard = state.uploads.lock().await;`) → 随后才执行 `multipart.next_field().await` (`L661`) 与 `field.bytes().await` (`L678`)
  - 原图访问拿锁：`apps/api/src/main.rs:1208` (`serve_image` 入口第一行即 `state.uploads.lock().await`)
  - 缩略图访问拿锁：`apps/api/src/thumbnails.rs:32` (`thumbnails::serve` 先占信号量再等 `state.uploads.lock().await`)
  - 迁移/导入任务拿锁：`apps/api/src/file_jobs.rs:433`
- **产生原因**：
  早期实现为了省事，用一把进程级 `Mutex<()>` 同时充当“配额串行锁”、“去重锁”、“文件读写锁”和“断连对账锁”（见 `tests/albums_http.py:139-146` 慢连接对账测试），甚至把耗时的客户端网络流读取、16000×16000 像素图片解码、缩略图实时渲染和只读原图输出全部塞进了同一个临界区。
- **实际危害**：
  1. **慢速攻击 / 弱网雪崩**：只要有 1 名登录用户在弱网环境上传几 MB 原图，或恶意保持一个半开的 `POST /api/v1/images` 连接（Axum 未对 multipart body 流设独立短超时），`state.uploads` 将被长时间独占；期间**全站所有公开图片外链 `/i/*`、所有图库缩略图、所有其他用户的上传与删除全部挂起无响应**。
  2. **缩略图并发形同虚设**：虽然 `AppState.thumbnails` 配置了 2 个并发信号量（`main.rs:1436`），但紧接着下一行就争抢唯一的 `uploads` 互斥锁，实际退化为全站单线程排队。

### 2. 【P0 安全/可用性漏洞】双层 Nginx 反代吞没真实 IP，登录/注册限流退化为全站共享单桶
- **精确位置**：
  - 容器入口拓扑：`deploy/compose.yml:45-53`（仅暴露 `web:8080`）+ `deploy/nginx.conf:19-23`（`proxy_pass http://api:3001;`，未传递任何客户端地址头）
  - 后端限流实现：`apps/api/src/main.rs:275-280` (`login`)、`main.rs:337-342` (`register`)、`apps/api/src/security.rs:438-442` (`passkey/start`)、`security.rs:470-474` (`passkey/finish`)
- **产生原因**：
  `main.rs:189` 注释写道 *“reverse-proxy clients share peer-IP limits”*，原意以为只是宿主机反代共享回环 IP；但在实际容器编排中，`api` 只接收来自 `web` 容器的 TCP 连接，`ConnectInfo(peer).ip()` **100% 恒等于 `web` 容器的 Docker 网桥 IP（如 `172.18.0.x`）**。更糟的是，`rate()` 在 `validate_credentials()` **之前**执行，且未按目标用户名区分失败计数。
- **实际危害**：
  1. 代码里写的 `login:global (120/min)` 和 `register:global (20/h)` 完全成了死代码——因为所有人共用同一个 `login:{web容器IP} (20/min)` 和 `register:{web容器IP} (5/h)`！
  2. 任意未登录攻击者无需消耗 Argon2 算力，仅需每分钟发送 20 个空密码/短密码请求，即可让**全站所有正常用户及管理员（含密码登录与 Passkey 登录）持续收到 `429 操作过于频繁`**，造成零成本全站登录拒绝服务。
  3. 同时，每次请求都会顺手执行全表扫描清理 `DELETE FROM rate_limits WHERE expires_at < NOW()`（`main.rs:191`），高并发下产生无谓的写放大与行锁竞争。

### 3. 【P1 可用性缺陷】`bootstrap` 启动强耦合待清理文件，单块次盘离线会导致全站拒绝启动
- **精确位置**：`apps/api/src/main.rs:1343-1351` & `main.rs:1445-1451`
- **产生原因**：
  `main()` 在监听端口前调用 `bootstrap(&state).await?`，其中遍历全部 `WHERE deleted_at IS NOT NULL` 的图片调用 `remove_file_record(state, &row).await?`，遇到任何单个 I/O 错误或挂载身份不符即直接 `?` 退出进程。
- **实际危害**：
  当管理员挂载了第二块扩展盘（如 `/storage/pictures`），若其中曾有 1 张待删除图片或中断上传，后续哪怕只是该次要挂载盘临时离线，整个 PicCove API 容器就会陷入无限重启循环，连默认主盘 `/data/uploads` 上的所有正常外链和管理员后台修复入口也一并瘫痪。

### 4. 【P1 运维与数据安全隐患】`piccovectl backup` 与 `update` 的多处状态机边界漏洞
- **精确位置**：
  - 备份逻辑：`apps/api/src/ctl/mod.rs:1084-1166`
  - 升级逻辑：`apps/api/src/ctl/mod.rs:1008-1056` & `ctl/mod.rs:1214-1218`
  - 宿主机管理器：`apps/api/src/ctl/web.rs:25-43` & `ctl/mod.rs:685-696`
- **产生原因与危害拆解**：
  1. **备份漏掉 `compose.override.yml`**：`DEPLOY-tu.jpggg.com.md:43` 与 `OPERATIONS.md:80` 明确指导管理员将外部存储挂载和宿主机 AI 上游映射（`extra_hosts: ["in.mb.al:host-gateway"]`）写入 `/opt/piccove/compose.override.yml`，但 `backup()` 只拷贝了 `[".env", "release.json", "compose.yml"]`（`L1127`），导致灾难恢复后 AI 上游和自定义挂载配置静默丢失。
  2. **备份停写前做外盘检查 + 清理失败不恢复服务**：`L1085` 在停止 `api` 前查询是否存在非 `/data/uploads` 图片（停写前仍可能发生新写入或迁移切盘）；且 `L1156` 清理临时备份容器使用 `?` 提前返回，若清理报错，原已停止的生产 `api`/`web` 容器将**跳过 `L1164` 的 `compose start` 直接保持停机**。
  3. **升级后清理失败反杀已就绪的新版服务**：`update()` 在 `L1009` 先停掉线上服务再慢速执行 `docker buildx` 构建镜像，拉长了停机时间；更严重的是，在 `L1016-1018` 新容器已启动、通过逐字节 `health()` 检查且已覆盖写入新 `release.json` 之后，若 `L1042` `prune_images` 删除旧镜像报错，仍会跳入 `L1046` 统一失败分支**把刚跑通的新版 `api` 和 `web` 强行 `stop`**，同时留下 `.piccove-update-pending.json` 导致 `piccovectl start` 也被拒绝！
  4. **自定义安装目录父级权限未核验**：`web-manager` 以宿主机 `root` 运行并执行 `<install_dir>/bin/piccovectl`（`ctl/web.rs:154`），`check_replacement` 校验了二进制自身属主，但 `create_program_dirs`（`ctl/mod.rs:685`）对自定义路径已存在的祖先目录未检查是否被非特权用户可写（默认 `/opt/piccove` 不受影响，自定义非标目录存在目录替换风险）。

### 5. 【P1 数据一致性缺陷】上传落盘异常与 AI 任务状态机的非原子窗口
- **精确位置**：
  - 上传落盘：`apps/api/src/main.rs:788-806`
  - 审核重入：`apps/api/src/ai.rs:298-301`、`ai.rs:561-570`
  - AI 生图回写：`apps/api/src/ai.rs:1000-1035`
- **产生原因与具体表现**：
  1. **`store_image` 写盘失败遗留幽灵记录**：`L788-791` 先提交事务插入 `deleted_at = NOW()` 的图片行并入队 `image_reviews`，随后 `L793` 调用 `dir.write_new`。若此时磁盘满或 I/O 报错返回 `Err`，该未落盘记录不会当场回滚删除，而是留在库中计入用户 `used_bytes` 配额、出现在普通图库列表（显示“待清理”），且触发审核 Worker 白白报错重试 3 次，直到下次重启服务才被清理。
  2. **AI 生图落盘与消息完成割裂 + 静默吞错**：`ai.rs:1002` 先完成 `store_image` 扣减用户存储配额，再于 `L1017` 单独 `UPDATE ai_messages SET status='completed'`；若中间连接闪断，用户白扣配额生成一张孤儿私有图，消息却丢失结果。而在生成报错分支（`L1033`），`let _ = sqlx::query("UPDATE ai_messages SET status='failed'...")` 直接忽略数据库错误——一旦写回偶发失败，该条消息将永久卡在 `running`，锁死当前对话（`请等待当前对话生成结束`）并永久占住并发与每日额度槽位。
  3. **历史审核失败哈希重传无法自动重审**：`enqueue_review` 使用 `ON CONFLICT(user_id, content_hash) DO NOTHING`（`ai.rs:298`）。若上游 AI 故障导致某图 `image_reviews.status = 'failed'`，用户删图后次日重传同一文件，审核状态会永远停留在旧的 `'failed'` 而不重新入队。此外管理员手动点“确认违规”（`ai.rs:566`）时硬编码 `categories: vec![]`，会把模型原本识别出的违规分类标签清空。
  4. **权限与错误分类小缺口**：`update_visibility`（`main.rs:864`）锁定用户行后只查了 `content_ban`，漏查了管理员并发设置的 `current.disabled`；`authorize_image`（`ai.rs:266`）用 `authenticate(...).await.ok()` 把数据库连接池超时等 5xx 故障也当成“未登录匿名访客”，对私有图返回误导性的 `404`。

### 6. 【P2 前端状态与口径不一致】软删除统计口径分裂、跨账号缓存闪现与错误处理越界
- **精确位置**：
  - `deleted_at` 多口径分裂：`main.rs:404` (`/me`)、`main.rs:579` (`list_images`)、`main.rs:1070-1073` (`admin_overview`)、`storage.rs:385` (`storage::list`)
  - 前端删除与预览兜底：`gallery-page.tsx:400-405`、`all-images-page.tsx:204-209`、`reviews-page.tsx:133-151`
  - React Query 键未隔离用户：`App.tsx:24`、`app-layout.tsx:121-129`、`gallery-page.tsx:173,193`
  - 事件重复绑定：`gallery-page.tsx:247-268`
- **产生原因**：
  1. `admin_overview` 中 `images_total` 过滤了 `WHERE deleted_at IS NULL`，但紧挨着的 `used_bytes` 与 `storage::list` 的 `COUNT(*)` 却未过滤 `deleted_at IS NULL`；普通图库浏览（未传 `ids`）也未过滤 `deleted_at IS NULL`，导致图库显示张数、相册统计张数与后台总览张数三者可能对不上。
  2. 前端 `DELETE` 捕获异常时写了 `if (!(err instanceof ApiError && [401, 403].includes(err.status))) removeImage(item.id)`，导致遇到 `500` 或网络断连时仍把本地上传记录删掉；`reviews-page.tsx` 查询图片详情失败时用空 `catch {}` 吞错并捏造 `width: 0, height: 0` 的假对象。
  3. `GalleryPage` 的 `document.addEventListener('paste', onPaste)` 漏写 `useEffect` 依赖数组，导致每次输入框打字或上传进度刷新都反复解绑/重绑全局粘贴监听器。
  4. 版本标识小盲区：当前 `HEAD (ef02019)` 已合入大型重构，但 `Cargo.toml` 与 `package.json` 版本号仍停留在已发版的 `0.1.14`，管理页不展示短 `commit` 号时难以区分运行实例是否包含新提交。

## 三、现有功能与工程体验瓶颈成因

1. **批量操作串行 N+1 放大**：`gallery-page.tsx` 与 `all-images-page.tsx` 的批量公开/私有、批量移动相册、批量删除全部采用 `for (const item of chosen) { await api(...); }` 串行请求。勾选一页 48 张图在公网 RTT 100~200ms 下需等待数秒至十余秒，且中途断网会停在半完成状态。
2. **首屏单包近 1 MB 且无 Nginx 压缩**：`App.tsx` 同步静态导入所有前台、AI 与管理后台重型组件（`admin/dist` 实测单包 JS **903,859 B**、CSS **150,495 B**），`vite.config.ts` 用 `chunkSizeWarningLimit: 3000` 掩盖大包告警，且 `deploy/nginx.conf` 未开启 `gzip`，首次打开登录页也要无压缩加载全部后台代码。
3. **公开图片与缩略图零浏览器缓存**：`serve_image` 与 `thumbnails::serve` 无差别下发 `Cache-Control: no-store`。对私有图和待审图这是安全的，但对已通过审核的公开图片和用户本人反复翻页查看的缩略图，每次切换路由都要重新拉取完整字节流。
4. **上传中心历史无限膨胀**：`upload-manager.tsx` 在上传完成后虽清空了 `File` 引用，但把完成态元数据永久保留在 IndexedDB `piccove-uploads` 中。长期使用后顶栏角标数字持续累加，且点击“复制本次链接”（`upload-center-sheet.tsx:82,144`）会把几天前未清空的历史链接一并复制出来。
5. **AI 创作台会话缺管理能力 & 轮询过度失效**：
   - 后端仅提供会话新建和读取，无法重命名或删除废弃/满 100 轮的会话；且 `ai.rs:931-938` 校验整段历史所有旧图，哪怕第 1 轮早已不参与上下文的旧图在图库被删，整段对话也会永久报错“请新建对话”。
   - 前端 `ai-studio-page.tsx:239-247` 只要消息列表里存在任意一条历史已完成消息，每次轮询都会全量 `invalidateQueries(['me', 'ai-status', 'images'])`；后端 `review_worker`（`ai.rs:513`）每审完 1 张图不论队列是否积压都固定 `sleep(2s)`，批量导入 1000 张图光空等就要 33 分钟以上。
6. **Android 客户端落后于服务端能力**：`MainActivity.java` 列表页仍直接下载最高 10 MiB 的 `/i/{id}` 原图在手机内存采样（未用现成的 `/api/v1/images/{id}/thumbnail`）；分享硬编码无扩展名的 `/i/{uuid}`（导致部分聊天/论坛无法识别图片后缀预览）；上传到指定相册仍拆成“先传再 PATCH”两步且 `PATCH` 全量回传旧字段。

## 四、AGY × Codex 交叉审查去伪存真记录

为严格落实“互补互助 + 防止 Codex 过度防御”原则，AGY 对 Codex 初审报告进行了逐条复核与纠偏：
